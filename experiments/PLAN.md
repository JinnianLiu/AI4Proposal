两者的一个结构性差别要在报告中说明：Claude Code 可以把工具精确限定为文件读写；Codex 的核心工具是 shell 命令，只能靠沙箱把它限制在工作目录内、禁止联网。所以 C1-CX 能在工作目录里执行命令（例如用命令统计字数），C1-CC 不能。

### 2.1 C1-CC：Claude Code 接 DeepSeek 的 Anthropic 兼容接口

DeepSeek 官方提供 Anthropic 兼容接口（`https://api.deepseek.com/anthropic`），并有接入 Claude Code 的说明，模型名可以直接写 `deepseek-flash`。

- **system prompt**：`--system-prompt-file` 把默认 system prompt 整个换成统一提示词，`--append-system-prompt-file` 再追加 C1 的工作方式说明。
- **工具**：`--tools "Read,Write,Edit"` 只保留文件读写。没有检索、没有命令执行、没有子智能体。
- **干净状态**：`--bare` 不加载 CLAUDE.md、记忆、MCP 和插件。
- **过程记录**：`--output-format stream-json` 保存完整过程（每轮输出和工具调用），可以据此统计轮数。

运行方式（PowerShell）：每个 task 开一个空的工作目录，在其中运行：

```powershell
$env:ANTHROPIC_BASE_URL  = "https://api.deepseek.com/anthropic"
$env:ANTHROPIC_AUTH_TOKEN = "<DeepSeek API key>"
claude -p --bare --model deepseek-flash `
  --system-prompt-file   <rendered>/task_XXX.system.md `
  --append-system-prompt-file <prompts>/c1_workspace.md `
  --tools "Read,Write,Edit" --permission-mode acceptEdits `
  --output-format stream-json --verbose `
  (Get-Content <rendered>/task_XXX.user.md -Raw) > transcript.jsonl
```

- 智能体把全文写入工作目录下的 `proposal.md`。
- 结束时如果 `proposal.md` 缺章，允许用 `claude -p --continue "请从中断处继续，完成 proposal.md 中缺少的章节，不要重复已写内容。"` 续跑，最多 2 次，并在生成记录表里记下次数。
- 运行前记录 `claude -v` 的版本号。

### 2.2 C1-CX：Codex CLI 接 DeepSeek

Codex 的自定义模型提供方只支持 `responses` 协议。项目自己的 [llm.py](../src/ai4proposal/llm.py) 注释里记录过 DeepSeek 端点同时支持 chat.completions 和 `/responses`，所以可以接入；冒烟检查时第一件事就是确认这一点。

**配置。** 每次运行用一个独立的 `CODEX_HOME` 目录（在该次运行的目录下），由 `run_c1.py` 自动生成。这样不会读到你个人的 Codex 配置（相当于 Claude Code 的 `--bare`），并行运行时不会互相覆盖配置，续跑也只会接上本次运行的会话。其中的 `config.toml`：

```toml
model = "deepseek-flash"
model_provider = "deepseek"
developer_instructions = '''<统一 system 提示词 + c1_workspace 追加段>'''   # 保留 Codex 内置指令，统一提示词以开发者指令注入
web_search = "disabled"
sandbox_mode = "workspace-write"                              # 只能写工作目录；该模式默认不联网
approval_policy = "never"
project_doc_max_bytes = 0                                     # 不读 AGENTS.md

[windows]
sandbox = "unelevated"                                        # Windows 必须开启原生沙箱，否则 workspace-write 会退化为只读

[model_providers.deepseek]
name = "DeepSeek"
base_url = "https://api.deepseek.com"
env_key = "DEEPSEEK_API_KEY"
wire_api = "responses"
```

**运行（PowerShell）。** 每个 task 开一个空的工作目录：

```powershell
$env:CODEX_HOME = "<本次运行目录>/codex_home"
$env:DEEPSEEK_API_KEY = "<DeepSeek API key>"
Get-Content <rendered>/task_XXX.user.md -Raw | codex exec `
  --cd <工作目录> -s workspace-write --skip-git-repo-check `
  --json -o last_message.txt - > transcript.jsonl
```

- 与 C1-CC 相同：全文写入 `proposal.md`；缺章时允许用 `codex exec resume --last "<同一句固定续跑语句>"` 续跑，最多 2 次；运行前记录 `codex --version`。

**冒烟检查结论（2026-09-30，task_001）。**

- **C1-CC**：整体替换内置 system prompt 后工作正常。
- **C1-CX**：原设计（`model_instructions_file` 整体替换内置指令）没有跑通，改动了两处：
  1. **保留 Codex 内置指令，统一提示词改以 `developer_instructions` 注入。** 智能体收到的课题信息和质量要求与 C4 相同，但另外还带着 Codex 自己的内置指令。所以 C1-CX 与 C4 的 system prompt 差别比 C1-CC 大，报告中要说明这一点。
  2. **开启 Windows 原生沙箱（`[windows] sandbox = "unelevated"`）。** 不开启时，`workspace-write` 会静默退化为只读，智能体的每一次写文件都被拒绝，一直写不出 `proposal.md`。这次失败的运行记录已被后续重跑覆盖。
- Codex 没有 deepseek-flash 的模型元数据，每轮都会给出一条警告；这不影响运行。

### 3.2 同一份输入与质量标准

- C1 和 C4 的 user 消息只包含流水线实际用到的字段。
- 统一提示词由流水线自己的写作提示词改写而来，只删去依赖流水线机制的条目，所以四个条件比的是架构，不是提示词质量。

### 3.3 正文评价不含配图，统一做后处理

- C2 不出图。C3 用 `--figures dry` 运行：只规划图件、保留图位标记，留给配图一致性评估那条线事后补图（§6.2）。
- 四个条件的正文都过同一个规范化脚本，只删不改，并记录每篇删了什么。删除范围：
  - 第一个 `#` 标题之前、最后一章之后的对话性文字；
  - 残留的 `[figure:]` 标记。

### 3.4 章节结构（structure）对评审的影响与处理

**影响在哪里。** 评审时，task 的 `structure` 会以"期望章节"的形式放进四位专家的公共提示词（`evaluation.py` 的 `_COMMON_HEADER`），影响三处：

1. **写作评委的逐节核对（`section_checklist`）**：有章节被判缺失，就会触发"缺失章节"硬闸，判定最高只能到 revise_resubmit。
2. **规范性维度的分档**：最高档的条件是"覆盖指南要求的全部章节与要素"。
3. **其他评委对全文组织的预期**：因为结构放在"指南硬性要求/约束"旁边，评委会把它当作指南的一部分来看。

**对没有给定结构的 task，现状是不公平的。**

- **流水线**：先现场规划一份结构，再写回自己输出目录下的 `task.json`。`evaluate.py` 读取的正是这份文件，所以流水线等于**按自己规划的结构接受核对**，必然全部对上。
- **基线**：输出目录里没有这份文件。如果给它原始 task，里面没有 `structure`，评审会退回代码里的默认章节表 `DEFAULT_CORE_SECTIONS`——一份按 task_001 写的中文章节名。英文 task 几乎必然被判"缺章"，触发硬闸，规范性维度也会被扣分。
- **v2 的做法**：把流水线规划的结构冻结下来给四个条件共用。这在条件之间是公平的，但还有两个问题：
  - 评委会把**流水线自己编的结构当成指南要求**；
  - 基线**白得了流水线的规划成果**，C3 的结构规划能力完全没有被测到。

**处理：结构尽量来自官方模板。** 12 个 task 中，11 个的结构来自或拟来自官方模板，1 个例外。

- 新增的 task_007–010 都选了指南有正文结构规定的资助计划。
- task_011 用国家自然科学基金申请书正文"立项依据与研究内容"的通用提纲。2026 年重大研究计划重点支持项目是否沿用这份提纲还待核对（2026 年的改版明确只适用于面上项目和青年 C 类）。
- **task_012 是唯一的例外**：它的具体指南方向在需要登录才能查看的附件里，拿不到官方模板，所以沿用你提供的结构，删去了生成范围之外的部分。四个条件用的是同一份结构，条件之间仍然公平；只是这个 task 的"期望章节"不来自指南，报告中单独说明。
- 现有的 task_003–006 改为从官方来源转写，不再用流水线规划的结构。修订版已冻结在 `tasks/`：
  - task_003：取自 Wellcome 申请表样表（2026-04-07 更新版），官方原文；
  - task_006：取自 NSF 25-508（已取代原来依据的 23-530），官方原文；
  - task_004、task_005：官方模板在需要登录的申报系统里，目前只能依据二手来源起草。需要你提供模板或按模板核对，否则这两个 task 也要列为例外。
- 转写来源记在各 task 的 `provenance` 里，由你核对。
- 这样"期望章节"真正来自指南：四个条件拿到同一份结构，评委核对的也是指南要求。
- 人工评审看到的章节结构同样标明来自官方模板。

**附带发现的一个问题**：流水线把 `word_limit` 统一渲染成"N字"。这对英文 task 有歧义，而英文 task 此前都没有给定结构，所以从未暴露。task_008 和 task_009 带了按单词计的上限，写代码时要为英文 task 渲染成 "N words"，统一提示词中的章节清单也一样（§10 第 2 步）。

## 5. 评审

**评审团组成。** 各固定到具体版本，写进 `judges.json`，实验期间不换：

**评审方式。**
- 每个评委模型独立跑一次完整的 `RubricPanel`（4 位专家加主席）；7 维分数、总分和判定都由代码计算。
- 评审团分数取三个评委的平均，同时列出每个评委各自的结果，看方向是否一致。
- 每篇文档每个评委评 1 次；另外抽约 1/4 的文档再评 1 次，估计各评委自身的打分噪声。
- 评审细则、权重和评委提示词在本阶段冻结，开跑前打 tag `exp1-freeze`。
- 冒烟检查时先确认三个评委都能稳定输出评审要求的 JSON 格式。

## 6. 人类一致性评估

### 6.1 正文：直接打分

**文档子集。** 从计算机评审人能评的 task 中选：001、007、008、009、010，共 5 个 task。task_011（航空宇航）不在两位评审人的领域内；task_012 只有闭环算法部分与计算机相关，不纳入。

每个 task 的 C1-CC、C2、C3、C4 各一篇，共 20 篇。C1-CX 不进人工子集，理由见 §11 第 2 项。

**评审人与安排。**
- 2 名评审人，每篇都由 2 人独立打分，用来计算人与人之间的一致性，作为评审团能达到的上限参照。
- 按每篇 40–90 分钟估计，每人约 13–30 小时。人手不够时缩到 4 个 task、16 篇。
- 正式打分前，2 人先各评 1 篇练习文档（不在子集内），对照分档锚点讨论一次，统一尺度。

**评分方式。**
- 使用与 LLM 评委相同的 7 维细则和五档锚点，每维打 1–10 的整数；总分由同一套权重算出。
- 另外独立给出一个三档判定：recommend_submit / revise_resubmit / reject。
- 评审人看到的材料：task 信息（标题、要求、约束、章节结构及其官方来源）加正文。
- 盲评：文件用随机编号，不告知由哪个系统生成、共有几个条件，也不给看 LLM 的分数。
- 评审顺序随机，同一 task 的几篇不连着评。
- 记录每篇用时；打 4 分及以下的维度，写一行理由。

**一致性指标。** 按总分和 7 个维度分别计算：

| 指标 | 含义 |
|---|---|
| 人–人 ICC(2,1) | 两名评审人之间的一致性，作为上限参照 |
| 评审团–人 Spearman ρ | 评审团均分与两人均分的相关 |
| 单个评委–人 Spearman ρ | 三个评委中哪个与人最接近 |
| 同一 task 内条件排序的 Kendall τ | 评审团与人对 4 个条件的排序是否一致；本实验最关心这一项 |
| 判定一致性（加权 κ） | 三档判定是否一致 |
| 系统性偏差 | 评审团分数减人工分数的平均值，看评审团整体偏松还是偏严 |

**判定标准（建议）。** 某个维度上，评审团与人的一致性达到人与人一致性的 80% 以上，就认为评审团在这个维度上可以替代人；达不到的维度在后续结论中不单独使用。20 篇的样本下，相关系数的 95% 置信区间大约有 ±0.3 宽，本阶段的结论是"够用 / 不够用 / 需要更多样本"。

### 6.2 配图评委

**沿用现有两个维度**：与正文的匹配度（good / partial / mismatch），图片表现（good / acceptable / poor）。视觉模型保持现有的 `deepseek-v4-flash-vision-exp`，不做模型对比。先按下面四点细化提示词，冻结后再做一致性评估。

**细化内容（已确定做这四点）：**

1. **给每个档位写锚点。** 现在只有档位名，没有定义（例如 partial 和 mismatch 的界线在哪）。正文评审的七个维度都有五档锚点，配图也应该有。人工评审要用同一份锚点，否则一致性无从谈起。
2. **把"编造数值"定义清楚。** 现在的 `fabricated_numbers` 会列出图中出现的所有数值。应改为"图中出现、但正文里没有的数值"，否则正文里本来就有的数值也会被当成编造。
3. **严重问题改成结构化字段。** 增加三个是否字段：乱码或不可读、编造数值、与正文矛盾。这样可以和人工标注一一对应，直接算精确率和召回率。
4. **区分两种"不匹配"。** 图与图注不符，和图与所在段落的论点不符，是两种问题。现在混在同一个维度里，至少要在 reason 里分开写。

**样本与打分。**
- 用 C3 规划好的图位补出图片，从中分层抽约 40 张，覆盖不同 task 和不同构图类型。
- 2 名评审人按细化后的锚点打两个维度，并标记三类严重问题。
- 评审人看到的材料与配图评委相同：图、图注、图所在的那段正文。

**一致性指标。**
- 两个维度各算加权 κ，包括人与人之间、配图评委与人之间。
- 三类严重问题各算配图评委相对于人工多数意见的精确率和召回率。召回率更重要：漏报严重问题比误报的代价大。

## 12. 已知局限

- **评审细则的主场优势。** 细则是在本流水线的产出上迭代出来的，C3 可能占便宜。人工评分是本阶段唯一的外部参照。
- **样本量小。** 12 个 task、20 篇人工评分，结论只能是方向性的。
- **人工子集只覆盖计算机相关的 task。** 一致性结论能否推广到人文、生物医学等 task，本阶段无法验证。
- **C4 可能被截断。** 长 task 上 C4 可能一次写不完，这是该架构的真实局限，截断情况单独统计。
- **flash 底座下没有任何现成数据。** 冒烟检查要特别看是否出现地板效应。
